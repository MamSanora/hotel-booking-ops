Baseline Analysis
Problem Statement & Legacy Pain Points
04 / 16
1. Manual Ledger Bookkeeping
  • Bookings recorded by hand in paper logbooks or standalone Excel files.
  • No standardized format — inconsistent records between receptionists.
  • Zero search functionality for past guest records or billing history.
2. Double-Booking & Inventory Loss
  • No real-time room availability sync between concurrent receptionists.
  • Rooms double-booked on peak weekends causing guest complaints.
  • Rooms left vacant due to slow record updates — lost revenue.
3. Fragmented Housekeeping Sync
  • Room states (Available / Occupied / Dirty) communicated via unstructured Telegram texts.
  • Front desk staff had no real-time visibility — guests waited unnecessarily.
  • Cleaning teams operated blind to upcoming check-in urgency.
4. Cash-Only Reconciliation Delays
  • Manual cash records caused daily reconciliation headaches and discrepancies.
  • No digital payment option — KHQR cashless transactions unavailable.
  • Management received delayed, inaccurate revenue reports for decision-making.

Data Engineering
Database Schema & Relational Architecture
10 / 16
Relational Schema (MySQL, 3NF)
room_types id, display_name, price_per_night, overbooking_multiplier, capacity rooms id, room_number, room_type_id [FK], current_status guests id, full_name, email, phone, gender, nationality bookings id, guest_id [FK], room_id [FK], check_in_date, check_out_date, booking_status, booked_by transactions id, booking_id [FK], amount_paid, payment_method, payment_status staff id, full_name, username, role, password_hash room_services id, booking_id [FK], request_type, status, notes
Design Principles
  • 3rd Normal Form (3NF): No transitive dependencies; eliminates data redundancy and update anomalies.
  • Referential Integrity: Strict FK constraints with explicit cascade and restriction policies.
  • Audit Timestamps: Auto-managed created_at & updated_at on all tables via Eloquent.
  • Soft Deletes: Safe record archival without permanent data loss for key entities.
  • Enum Columns: Controlled status values enforced at DB level for bookings, payments, and rooms.

Algorithmic Innovation
Stochastic Overbooking Optimization Engine
13 / 16
Heuristic Model Design
  • Command: app:optimize-overbooking
  • Scheduled: Nightly at 02:05 AM (post-night audit)
  • Theory: Talluri & van Ryzin, Ch.4 — Stochastic Approximation

Self-Tuning Feedback Loop:

  • PENALTY (−0.05): Relocations > 0 yesterday → overbooking too aggressive → reduce multiplier.
  • REWARD (+0.01): No-shows > 0 + zero relocations → played too safe → increase multiplier.
  • NEUTRAL (0.00): No signal → multiplier unchanged.

Safety Bounds: 1.00 ≤ multiplier ≤ 1.50

Laravel Implementation
$yesterdayBookings = Booking::whereHas( 'room', fn($q) => $q->where( 'room_type_id', $roomType->id) )->whereDate('check_in_date', $yesterday) ->get(); $relocations = $yesterdayBookings ->where('status', STATUS_RELOCATED) ->count(); $noShows = $yesterdayBookings ->where('status', STATUS_NO_SHOW) ->count(); if ($relocations > 0) { $adjusted -= 0.05; // Penalty } elseif ($noShows > 0) { $adjusted += 0.01; // Reward } $roomType->overbooking_multiplier = min(1.50, max(1.00, $adjusted));
